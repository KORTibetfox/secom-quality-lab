# 개발·검증에서 발생한 문제와 해결 기록

## 완료 범위

v1은 분석/모델 실험, v2는 같은 모델을 사용하는 로컬 shadow 운영 계층이다.
v2에서 기존 최종 평가 결과를 보고 모델을 교체하거나 성능을 재포장하지 않았다.
문제를 고쳤다는 것과 현장 사업 성과를 검증했다는 것을 구분한다.

아래 **관측**은 실제 데이터·실행·테스트에서 확인한 문제이며, **예방**은 운영 중 발생할 수 있는 실패를 테스트/계약으로 대비한 설계다.

## 운영 실패를 예방한 설계

| 구분 | 문제 | 방법 | 선택 이유/검증 |
|---|---|---|---|
| 예방 | 센서 수·숫자 형식·중복 ID·불명 필드 | Pydantic strict 계약과 명시적 숫자 검사 | 590열, string/bool/Infinity, 빈/101행 배치, 중복 ID 거부를 실제 HTTP 테스트 |
| 예방 | 대부분 입력이 결측인데 대체값만으로 그럴듯한 점수 생성 | usable 센서 행별 결측률>50% 거부 | 기존 검사 정책 유지. 기준은 실제 공정에서 재검증 필요 |
| 예방 | 대형 JSON이 메모리와 CPU를 점유 | ASGI에서 누적 2 MiB 제한 후 파싱 | 본문 초과에 413 응답 테스트. 공개 인터넷 DDoS 방어용은 아님 |
| 예방 | 외부 노출·무인증 호출 | 127.0.0.1 고정, 충분히 긴 로컬 토큰, constant-time 비교, 공개 docs 비활성 | 무인증 readiness/추론 401 확인. localhost 외 서비스·SSO/TLS 미구현 |
| 예방 | 동시에 같은 요청을 재시도해 서로 다른 순위/중복 처리 | 입력+release digest, SQLite BEGIN IMMEDIATE, request_id 고유키 | 동시 두 호출에서 새 결과 하나와 replay 하나 확인. 보존 1,000건 내 보장 |
| 예방 | 같은 ID에 다른 데이터나 release 사용 | digest 불일치 409 | 잘못된 캐시 결과 반환 방지 |
| 예방 | 서비스 재시작 때 재시도 정보 소실 | 파일 SQLite, WAL, synchronous FULL | Runtime 재생성 후 replay 유지 테스트. DB 백업은 별도 운영 작업 |
| 예방 | 모델 파일 교체/부분 손상/패키지 불일치 | immutable release, manifest/payload 해시, 핵심 패키지 버전 확인 | 파일 끝에 손상 바이트를 넣은 복사본을 load 전에 거부. 해시는 서명/악의적 변조 방어가 아님 |
| 예방 | 과도한 병렬 추론·DB 잠금이 무한 대기를 유발 | 추론 semaphore 2, DB timeout 2초, 서비스 연결 한도 8 | 포화·DB 쓰기 잠금 시 503 확인. 무제한 스레드/큐를 만들지 않음 |
| 예방 | 에러 응답/로그로 원본 센서나 token 노출 | 일반화된 오류와 이벤트 종류만 저장, access log 비활성 | schema 오류 응답에 입력 배열을 반사하지 않음. DB 결과에는 추적용 unit ID가 남음 |
| 예방 | 운영 로그·캐시 무제한 증가 | 요청 1,000건/이벤트 10,000건 상한 | 최근 상태 기준 metric임을 명시. 만료 request ID의 무기한 중복 방지는 지원하지 않음 |
| 예방 | 분포 변화에도 점수만 계속 사용 | 개발 기준 결측률/분위 범위와 비교, 작은 배치 경고 | 경고를 반환하되 자동 재학습·모델 승격은 하지 않음. 임계값은 탐색용 |
| 예방 | label 지연/누락으로 성능을 과대평가 | 요청·unit 키 1:1 결합, coverage, 클래스 수 표시 | unknown key 거부, 단일 클래스 AP null 테스트. 선택적 label 수집 편향은 여전히 조사 필요 |
| 예방 | API 결과가 실제 검사 생략·출하 지시로 사용 | shadow_only, production_approved=false, shadow_priority 필드 | 건강 상태·실제 응답 테스트에서 gate 확인. 다운스트림 시스템도 계약을 준수해야 함 |

## 실제 검증 증거와 범위

- `results/operations_test_report.txt`: 데이터/계산 5개, 실제 HTTP/운영 통합 11개, 총 16개 테스트.
- `results/operations_smoke.json`: 실제 localhost 20행 배치 30회 직렬 호출. warm p95 약 32ms.
  단일 PC·샘플 데이터의 한 번 측정이며 운영 SLA나 대량 동시 처리 성능은 아니다.
- `results/feedback_report.json`: 알려진 holdout label을 사용한 **결합 기능 데모**. 새로운 현장 성능 검증이 아니다.
- `results/validation.json`: 원본 해시, 시간 분리, 지표/검사 예산/비용/저장 모델 대조.
- 실제 네트워크 API, 동시 동일 요청, 포화, SQLite 잠금, 파일 손상은 테스트했다.
  정전·디스크 가득 참·여러 서버·컨테이너·실제 MES 연동·현장 장기 운영은 실행하지 않았다.

## 의사결정

1. 최신 대형 모델 추가보다 입력 계약·시간 검증·운영 추적을 우선했다. 현재 제약은 모델 복잡도보다 유효한 평가와 데이터다.
2. 단일 PC에는 별도 Redis/PostgreSQL/Kubernetes 대신 SQLite를 선택했다. 서비스가 다중 서버로 커지면 이 경계는 재설계해야 한다.
3. 실제 품질 판정 승인을 주장하지 않고, 업무 시스템에 붙여 검증 가능한 shadow 도구를 완성했다.
4. 현장 데이터와 책임자 기준이 확보되면 독립 평가 → 비용/확률 보정 → shadow 검증 → 제한된 적용 순서로 진행한다.

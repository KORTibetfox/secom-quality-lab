# 면접에서 설명할 방향

## v2 운영 계층까지 설명하기

모델 성능만 설명하는 대신 “업무 시스템에서 안전하게 검증하려면 무엇이 필요한가”까지 이어간다.
다음 내용은 실제 코드와 테스트를 읽고 재실행한 뒤 설명한다.

- **데이터 계약:** 590개 센서 순서·숫자/null·ID·배치 크기를 검사하고 잘못된 입력을 거부했다.
- **재시도:** 네트워크가 끊긴 뒤 같은 요청을 보내도 결과가 바뀌지 않도록 request ID와 입력 digest를 저장했다.
- **원자성:** 결과와 이력을 SQLite 트랜잭션에 저장했다. Windows에서 연결이 닫히지 않던 오류도 원인을 찾아 수정했다.
- **변경 관리:** 모델·전처리·기준 분포·환경을 release로 묶고 손상 파일을 로드 전에 거부했다.
- **장애 대응:** DB 잠금과 추론 포화 때 503을 반환하고 기존 검사 정책을 유지하도록 계약했다.
- **관측:** 센서 분포 경고와 운영 지표, 지연 label 결합 및 label coverage를 제공했다.
- **검증:** 16개 테스트 및 20행×30회 실제 HTTP 호출을 확인했다. 단일 PC 지연시간을 생산 SLA로 주장하지 않는다.
- **범위:** shadow 연결 도구까지 구현했고 현장 품질 판정용 모델 승인까지 얻은 것은 아니다.

“왜 Kubernetes나 Redis를 쓰지 않았는가?”에는 단일 PC 요구에서 운영 의존성과 장애 지점을 늘릴 이유가 없었고,
다중 서버·장기 저장·고가용성 요구가 생기면 별도 상태 저장소와 인증/배포 설계가 필요하다고 설명한다.
자세한 사건별 기록은 `ENGINEERING_LOG.md`, 운영 절차는 `OPERATIONS.md`를 참고한다.

## 중심 메시지

“반도체 AI를 단순 분류 문제가 아니라 **검사 자원을 배분하는 문제**로 정의했고,
시간을 분리한 검증에서 성능 저하를 발견해 배포 판단을 보류했습니다.”

AI 지원으로 구현한 프로젝트다. 아래 설명은 본인이 코드를 읽고, 실험을 재실행하고,
각 선택을 설명할 수 있게 된 뒤 자신의 경험에 맞게 사용한다. 직접 하지 않은 일을 했다고 표현하지 않는다.

## 60초 설명 예시

이 프로젝트에서는 반도체 공정 데이터로 어떤 샘플을 먼저 검사할지 결정하는 시스템을 만들었습니다.
SECOM은 불량이 104개뿐인 불균형 데이터여서 정확도 대신 AP와 검사량별 불량 검출률을 사용했습니다.
전처리는 각 학습 fold 안에서 수행하고 마지막 시점 314개는 모델 선택에서 제외했습니다.
개발 구간에서 선택된 LightGBM의 AP가 미래 구간에서는 0.067로 떨어졌고,
상위 32개 검사에서 불량은 2개로, 무작위 기대치 1.73개와 큰 차이가 없었습니다.
그래서 높은 성능을 주장하는 대신 시간별 검증과 센서 분포 차이를 추가로 확인했습니다.
실제 현장에서는 최신 lot·장비 정보와 데이터 가용 시점을 확인한 후 shadow 운영으로 검증해야 한다고 판단했습니다.

## 예상 질문과 답변의 근거

### 왜 정확도를 주 지표로 쓰지 않았나요?

전체 데이터에서 모두 정상이라고 하면 1463/1567, 약 93.4%가 맞는다.
불량 검출에는 유용하지 않으므로 양성을 불량으로 고정하고 AP, 검출률, precision, FP/FN을 함께 봤다.
AP는 사다리꼴 PR-AUC와 계산식이 다르므로 이름을 혼용하지 않는다.

### 모델이 좋아졌다고 볼 수 있나요?

선택 모델의 최종 AP 0.0666은 무작위 기준 0.0541에 가깝고,
10% 검사 정책에서 2/17개 발견은 충분한 성과가 아니다.
검사 정책의 분모·발견 수와 불확실성을 공개했으며 실제 수율·비용 개선 주장을 하지 않는다.

### 왜 최종 결과가 더 좋은 로지스틱 회귀를 선택하지 않았나요?

로지스틱 회귀 C=0.1은 최종 AP 0.2221이지만 그 결과를 보고 교체하면 holdout이 모델 선택에 사용된다.
이번 선택 기준은 미리 정한 개발 AP였다. 후속 개선은 탐색이라고 표시하고 독립된 새 데이터에서 확인해야 한다.

### 미래 구간에서 실패한 원인은 무엇인가요?

확정하지 않았다. 개발/최종 구간에서 590개 센서 중 171개는 KS 거리 0.2 이상,
56개는 결측률 차이가 10%p 이상이었다. 개발 구간 내부 시간 검증에서도 성능이 변했다.
이는 분포 변화 가설의 단서이지 원인 증명이 아니다. 표본 부족·숨은 lot 의존성도 확인할 필요가 있다.
KS 기준은 탐색용이며 유의성이나 물리적 인과성을 의미하지 않는다.

### 결측값 처리에서 누수를 어떻게 막았나요?

센서 제거 여부, 중앙값, 스케일러는 Pipeline에서 각 학습 fold만 보고 fit했다.
최종 모델은 개발 구간만 fit했다. 저장 모델의 중앙값이 실제 개발 구간 중앙값과 일치하는지 검증했다.
전체 결측 통계는 감사용 그림에만 사용했다.

### 검사량 10%는 정확히 몇 개인가요?

314×0.1을 올림하여 32개(10.19%)다. 결과에 이 수를 표시했다.
점수 동점은 label을 사용하지 않는 row ID 해시로 처리한다. 실제 현장에서는 사업 규칙으로 대체한다.

### 점수를 불량 확률이라고 불러도 되나요?

아니다. class weighting·모델 구조 등에 따라 점수 스케일이 달라지고 보정도 수행하지 않았다.
이번에는 순위와 개발에서 선택한 경험적 비용 임계값으로 사용했다.
확률이 필요하면 학습/보정/평가 구간을 분리하고 reliability diagram·Brier score 등으로 검증한다.

### Isolation Forest를 넣은 이유는 무엇인가요?

불량 label이 부족한 상황의 보조 비교다. 정상 개발 데이터만 학습하고 음의 score_samples로 이상 정도를 계산했다.
최종 평가를 보고 선택 모델로 바꾸지 않았다. 이번 데이터에서 이상치가 곧 불량이라는 보장은 없었다.

### 최신 논문은 어떻게 활용했나요?

비용 민감 Transformer 연구의 문제 정의와 비용 평가를 참고했다.
TabPFN·TabM·VAE–SHAP는 후속 확장 후보이며 이번에 실행·재현한 모델이라고 말하지 않는다.
복잡한 모델 추가보다 시간·lot 단위로 유지되는 신호를 검증하는 것을 우선했다.

### 이 회사 업무와 어떻게 연결되나요?

불량률 예측은 샘플별 위험 순위 및 일정 기간의 예측·실측 비교로,
이상 탐지는 정상 공정 기반 보조 모델로, 파이프라인은 스키마 검증·재현 가능한 전처리·실험 기록으로 연결된다.
회사 내부 원천기술이나 반도체 신뢰성 수명 예측을 재현했다고 주장하지 않는다.

## 다음 개선안의 우선순위

1. 센서의 의미·가용 시점, lot·장비·레시피 ID를 확보해 누수와 그룹 상관관계를 점검한다.
2. 개발 구간에서만 시간 검증 기반 선택 전략을 설계한다. 이미 공개한 최종 구간은 새 검증 데이터로 재사용하지 않는다.
3. 최신 데이터로 독립 평가 및 shadow 운영을 수행한다. 실제 미탐·재검사 비용과 지연시간을 측정한다.
4. 그 뒤 TabPFN/TabM, 변수 선택, 확률 보정, 필요할 경우 합성 증강을 같은 예산에서 비교한다.

## 면접 전 직접 해볼 것

- `quality.py`에서 양성 label, 학습 내부 전처리, 검사량 올림, 비용 계산 코드를 설명한다.
- 테스트와 `verify`를 실행하고 결과 파일 한 행을 원본 label에서 손으로 확인한다.
- “왜 모델을 더 좋은 것으로 바꾸지 않았나”를 데이터 누수와 holdout의 역할로 설명한다.
- 회사에 “유료 운영 모델은 어떤 lot/장비/시간 분할로 평가하는가”와 “모든 입력이 추론 시점에 가용한가”를 묻는다.

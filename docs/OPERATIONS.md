# 로컬 shadow 운영 매뉴얼 · v2

## 준비 상태와 적용 범위

이 버전은 로컬 시스템과 연결해 **기존 품질 정책을 유지한 채 예측을 관찰하는 shadow 서비스**다.
서비스 구현의 완성도와 모델의 제조 현장 유효성은 별개다. v1의 최종 시간 AP는 0.0666,
32개 우선 검사에서 불량 2/17개로 실제 품질 판정에 사용할 근거가 부족하다.
`production_approved=false`는 모든 추론 응답에 들어가며 현장 시스템은 이 값을 반드시 확인해야 한다.
이 API의 `shadow_priority`는 참고 우선순위이며 출하 승인·검사 생략 명령이 아니다.

## 기동과 종료

PowerShell에서 프로젝트 폴더로 이동한다. `setup.ps1`은 새 PC용 환경 설치이고 현재 PC에는 환경이 있다.

```powershell
./run.ps1 -Action test
./run.ps1 -Action verify
./run.ps1 -Action serve
```

서버는 127.0.0.1:8766에만 바인딩한다. 종료는 서버 터미널에서 Ctrl+C.
별도 PowerShell 터미널에서 다음 명령으로 실제 HTTP 클라이언트를 실행한다.

```powershell
./run.ps1 -Action api-demo
./run.ps1 -Action smoke
```

인증 토큰은 최초 실행 시 `state/.api_token`에 생성한다. 로그나 예제 파일에 출력하지 않는다.
이 파일과 SQLite DB는 배포 ZIP 및 Git 대상에서 제외한다. 파일 접근은 현재 Windows 계정 권한에 의존한다.
공유 PC의 계정/ACL 검토가 필요하다. 외부 접속·공개 서비스·TLS·SSO 구성은 이번 범위에 포함하지 않았다.
토큰 교체는 서비스를 중단한 후 토큰 파일에 새 충분히 긴 난수를 저장하고 서비스를 다시 시작한다.
`SECOM_API_TOKEN` 환경변수를 설정한 경우 서버는 이를 우선 사용한다. 예제 client는 로컬 토큰 파일을 사용한다.

## API 계약

| 경로 | 인증 | 의미 |
|---|---|---|
| GET /health/live | 없음 | 프로세스 응답 |
| GET /health/ready | X-API-Key | 모델 기동 및 SQLite 읽기 확인 |
| POST /v1/rank | X-API-Key | 배치 내 우선순위 산출 |
| GET /v1/metrics | X-API-Key | 보존 중인 호출 수·평균/최대 지연·오류 종류 |

요청은 `request_id`, `inspection_fraction`(0~1), `units`(1~100개)로 구성한다.
각 unit은 고유 `unit_id`와 **sensor_000부터 sensor_589 순서의 590개 숫자/null 배열**이다.
샘플은 `src/client.py`를 참조한다. CSV 클라이언트는 열 이름과 순서도 검증한다.
단위 ID는 영문·숫자·`_.:-`의 1~64자, request_id는 동일 문자집합의 1~80자다.
서로 다른 배치의 우선순위는 직접 합산할 수 없다. 실제 검사를 배분할 운영 창과 배치 경계를 먼저 합의해야 한다.

문자형 숫자, boolean 센서, NaN/Infinity, 과도한 결측, 중복 ID, 알 수 없는 필드는 거부한다.
원본의 제거 대상 센서를 제외한 **학습에 사용한 센서의 결측률이 행별 50% 초과**이면 거부한다.
이 50% 및 모니터링 기준은 운영용 보수적 가정이며 현장 데이터로 정한 SLA가 아니다.
2 MiB 초과 본문은 JSON 파싱 전에 413으로 거부한다. 동시에 수행하는 추론은 최대 2개이며
uvicorn 연결 동시성 한도는 8개다. 단일 프로세스 전용 설계다.

| 코드 | 처리 |
|---|---|
| 200 | 결과 수신. shadow 상태를 확인하고 참고 정보로 기록 |
| 401 | 토큰 확인. 센서 payload나 토큰을 로그에 복사하지 않음 |
| 409 | 동일 request_id로 입력/모델 버전이 달라짐. 원본 요청을 확인 |
| 413/422 | 입력 수정 전 재시도 금지. 기존 검사 정책 유지 |
| 503 | 용량 또는 DB 상태 확인. 같은 request_id로 지수 backoff 후 제한적으로 재시도 |
| 500/timeout | 기존 검사 정책 유지. 같은 request_id로 조회/재시도하고 원인 조사 |

요청 ID는 재시도 시 유지한다. SQLite 트랜잭션에 결과와 이벤트를 함께 커밋한다.
응답 직전 연결이 끊겨도 동일 ID/동일 payload/동일 release의 재시도에는 저장된 결과를 준다.
입력이 바뀌면 409이다. 이 보장은 보존된 최근 1,000개 요청 범위이며 무기한 exactly-once가 아니다.
영속 request ID가 없는 기존 배치 CLI와 달리 API는 안정적인 실제 MES ID를 요구한다.
예제의 demo ID는 교육용이며 현장 ID로 교체해야 한다.

## 모델 변경과 롤백

`releases/active.json`은 버전과 manifest 해시를 가리킨다. 모델·스키마·기준 분포·환경 버전·선택 기록은
변경 금지 release 폴더에 함께 저장한다. 프로세스 시작 시 해시 및 주요 패키지 버전이 다르면 로드하지 않는다.
같은 버전 export는 덮어쓰지 않고 실패한다. 학습 결과를 갱신했다고 서버가 자동으로 바뀌지 않는다.

새 모델은 학습·검증 후 `run.ps1 -Action release`로 별도 release를 만든다. 이 명령은 active pointer도 갱신하므로
서버를 중단하고 변경 작업을 수행한 뒤 재기동·smoke 확인한다. 한 번 export한 동일 모델은 다시 export할 필요 없다.
롤백은 서버 중단 → 검증된 이전 폴더의 manifest SHA-256을 계산 → active pointer를 이전 버전/해시로 교체 → 재기동 순서다.
현재 제공 모델은 한 버전이므로 실제 과거 모델로의 롤백 사례는 실행하지 않았다.

해시는 실수/손상을 검출할 뿐 서명이나 공급망 보증이 아니다. joblib은 실행 가능한 직렬화이므로
외부에서 받은 임의 파일을 이 폴더에 넣지 않는다. Windows 계정 및 release 경로에 대한 쓰기 권한이 신뢰 경계다.

## 모니터링과 지연 label

요청별 센서 원문은 DB에 저장하지 않는다. 입력 digest, unit ID, 점수, 우선순위, release, 시각, 지연을 저장한다.
최대 최근 1,000개 요청 및 10,000개 이벤트를 유지한다. 일 단위 보존이나 자동 백업 정책은 아니다.
보존 범위가 업무에 짧으면 현장 보존 정책에 맞춘 별도 저장소가 필요하다.

개발 데이터의 센서별 결측률과 1~99 분위 범위를 release에 고정했다.
범위 외 값 비율 >10%, 결측률이 20%p 초과 변한 센서 >20개이면 검토 경고를 반환한다.
30개 미만 배치는 모니터링이 불안정하다고 표시한다. 경고는 탐색용이며 공정 이상 확정/자동 재학습 조건이 아니다.

최종 검사 label이 나중에 도착하면 `request_id,unit_id,label` CSV를 준비한다.

```powershell
./.venv/Scripts/python.exe src/evaluate_feedback.py --labels data/demo_feedback.csv
```

예측 키와 1:1 결합하고, 미등록/만료된 키나 중복 label은 거부한다. label coverage와 클래스 수를 표시한다.
한 클래스밖에 없으면 AP는 null이다. label이 늦거나 누락되면 그 자체로 편향이 생길 수 있다.
예제 feedback은 원본 holdout의 알려진 label로 만든 데모이며 신규 현장 실증이 아니다.

## 장애 대응

모델 해시 불일치: 기동 중단, 원본 release 복구. 검증을 끄거나 새 해시를 임의로 승인하지 않는다.
DB 쓰기 불가/잠금: readiness/요청 상태를 점검하고 저장 장치와 남은 용량 확인. 기존 검사 정책 유지.
프로세스 재시작: 같은 state 경로로 재기동하면 보존 요청의 재시도 결과가 유지된다.
백업: 서비스를 중단한 후 state 디렉터리 전체를 보안 저장소에 복사한다. 서비스 실행 중 SQLite 본체만 복사하면 WAL이 빠질 수 있다.
복구: 중단된 서비스의 state를 백업본으로 복원 → readiness → 기존 요청 ID 재시도 확인.
원인 진단에는 `results/operations_smoke.json`, `results/operations_test_report.txt`, `/v1/metrics`를 사용한다.

## 현장 적용 전에 남은 승인 조건

센서 정의·가용 시점과 MES 연결 규약, lot/장비/시간 분리 독립 평가, 최근 불량 label,
실제 검사 비용·운영 창·배치 정책, 품질 책임자의 승인, 현장 보안/백업/지연 기준을 확인해야 한다.
현재 패키지를 그 조건이 충족된 생산 자동 판정 시스템이라고 표현하면 안 된다.
